# Stage 2 — ручная проверка

Этот документ — план приёмки, а не запись уже пройденного тестирования. В среде подготовки ZIP не было работающей Android-сборки или эмулятора.

## Подготовка

Используйте Android Studio с рабочей конфигурацией Stage 1. Основной сценарий — API 33+ с Chrome/браузером в обычном полноэкранном режиме; дополнительно проверьте API 26–30, API 31–32 и API 24–25 (на последних ожидаются только уведомления). Проверьте навигацию и жестами, и тремя кнопками. В Google Play для foreground service specialUse существуют отдельные требования к публикации.

Из корня проекта:

```bash
./gradlew testDebugUnitTest
./gradlew assembleDebug
./gradlew connectedDebugAndroidTest
```

Последняя команда требует запущенного эмулятора/устройства. Windows: замените `./gradlew` на `gradlew.bat`. Unit suite: 72 объявленных теста; Android suite: 13. Дополнительно выполните STAGE2_UI_REVISION_TEST.md. APK после успешной сборки: `app/build/outputs/apk/debug/app-debug.apk`.

Для чистого сценария используйте отдельный эмулятор. Для миграции — отдельно установите Stage 1, создайте данные и затем Stage 2 поверх него с тем же ключом. Не удаляйте Stage 1 и не очищайте данные для проверки миграции.

## Главный сценарий — 26 шагов

1. Запустите ProjectADHD: видны тёмная тема, исходный фон и idle-маскот; изображение не растянуто.
2. Откройте Главная → шестерёнка → Разрешения; выдайте Usage Access, вернитесь и проверьте обновившийся статус.
3. Выдайте уведомления, разрешите оба канала. На API <33 отдельного runtime-запроса нет.
4. Нажмите «Разрешить поверх приложений». Включите ProjectADHD на системном экране и вернитесь. На Android 11+ может открыться общий список.
5. Создайте минимум две активные привычки на вкладке «Привычки».
6. Оставьте обе невыполненными. Главная показывает 0 из 2, осталось 2.
7. Выберите Chrome/тестовое приложение на вкладке приложений. Проверьте настоящую иконку Chrome, display name и package name, переключатель и лимит.
8. Установите лимит сессии 1 минута.
9. Запустите мониторинг на Главной. Есть постоянное уведомление с STOP.
10. Откройте тестовое приложение и пользуйтесь им непрерывно.
11. Дождитесь минуты плюс обычной задержки получения событий.
12. Появляется BLOCK: реальное приложение видно через фиолетовый scrim, недовольный маскот, имя приложения, длительность и осталось 2 задачи.
13. Касания по центру, краям и свободным областям окна не активируют содержимое приложения под ним. Кнопка задач работает. Нет обычной кнопки «Продолжить всё равно».
14. Нажмите системный Home/сделайте жест Home.
15. Окно скрывается после обработки смены foreground; launcher и другие приложения доступны. Измерьте задержку — ожидается около периода опроса плюс задержка Android, не гарантированные 0 ms.
16. Откройте заблокированное приложение снова, до выполнения задачи.
17. BLOCK возвращается без ожидания ещё одной минуты; в истории нет второго BLOCK_TRIGGERED для того же challenge.
18. Нажмите «Посмотреть дела». Открывается существующая MainActivity на привычках, overlay над ней отсутствует. Сам переход не снимает challenge.
19. Выполните одну из ранее незавершённых привычек.
20. Вернитесь к тестовому приложению.
21. Окна нет, в истории есть BLOCK_RELEASED с COMPLETION, active block закрыт.
22. Проверьте новый полный интервал: спустя несколько секунд BLOCK отсутствует; после новой минуты при одной оставшейся задаче он снова допустим.
23. Откройте привычки и выполните оставшуюся задачу. Сегодня 2 из 2.
24. Вернитесь в тестовое приложение и снова достигните лимита новой сессии.
25. Показывается PRAISE с отдельным радостным маскотом и текстом похвалы; окно исчезает примерно через 4 секунды.
26. Приложение остаётся доступным: касания проходят, активная BlockSession не появляется. Следующие опросы не повторяют Praise во время cooldown.

## Новое выполнение, старые отметки и данные

| Проверка | Действия | Ожидаемый результат |
| --- | --- | --- |
| Старая completed-задача | До BLOCK выполните A, оставьте B/C. При BLOCK снимите и верните отметку A | Блокировка остаётся; выполните B — снимается |
| Повторная отметка | Повторите setCompleted(true) для уже выполненной задачи в Android-тесте | INSERT IGNORE, нового release нет |
| Быстрый undo | После настоящего нового выполнения сразу снимите отметку до очередного poll | Записанный release остаётся; время нового интервала сохранено |
| Новая задача после BLOCK | Создайте D уже после challenge, выполните её, оставьте baseline B | D не снимает challenge; для release выполните B — привычку из baseline |
| Несколько приложений | Доведите до BLOCK два приложения с общей незавершённой B | По одному challenge на пакет, окно только над текущим; выполнение B освобождает оба |
| Удаление/архивирование | Уберите все baseline-задачи | Challenge отменяется как TASKS_CHANGED или NO_TASKS, а не COMPLETION; тупика нет |
| Нулевые задачи | Нет активных привычек, лимит превышен | NONE; нет просьбы выполнить несуществующую задачу |
| Все выполнены | Есть хотя бы одна активная привычка, все выполнены | Только PRAISE после лимита/cooldown |
| Новый день | Создайте challenge, смените локальную дату | Старый challenge закрывается NEW_DAY; задачи берутся по новой дате |
| Отключение приложения | Снимите отслеживание при active block | Challenge отменяется TRACKING_DISABLED, окно не возвращается |

## Разрешения, fallback и остановка

1. Без overlay permission запустите мониторинг и достигните лимита при incomplete > 0. Ожидаются active challenge, обычное уведомление, FALLBACK_NOTIFICATION, ошибка OVERLAY_PERMISSION_MISSING в Debug. Ввести permission можно позже: при возврате в blocked app появится окно.
2. Для проверки повторов установите паузу fallback 1 минуту. Не должно быть уведомлений каждый poll. Очистка истории не сбрасывает cooldown.
3. Отзовите overlay permission во время BLOCK через системные Settings. Окно должно исчезнуть, приложение не падает. В зависимости от Android сервис может быть остановлен системой; при необходимости запустите его вручную. При следующем BLOCK без permission ожидается fallback.
4. Отзовите Usage Access: мониторинг останавливается, overlay удаляется, причина видна на Главной/Debug.
5. Запретите уведомления/канал: Stage 1 правило запуска сохранено — мониторинг не запускается или останавливается, окно удаляется.
6. Нажмите STOP в Settings во время active block. Проверяйте одновременно отсутствие окна, active rows и foreground notification. Повторный запуск не должен вернуть старый challenge.
7. Повторите STOP из постоянного уведомления и Debug. Проверяйте отсутствие повторного создания challenge из завершающегося poll.
8. Повторяйте старт/стоп и вход/выход из blocked app 10 раз. Не должно быть дублирующихся окон, зависшего overlay или нескольких сервисов.
9. Откройте Settings, launcher, permission controller, системную шторку и ProjectADHD. Эти поверхности не должны целенаправленно блокироваться. Не выдавайте разрешения за другого пользователя через ADB вместо реального UI-сценария.
10. На API 24–25 достигните лимита: ожидается API_BELOW_26 и notification fallback, без legacy window-type hacks.

## Жизненный цикл и миграция

- При active block поверните экран ProjectADHD/пересоздайте Activity: challenge сохраняется, собственная Activity доступна.
- Удалите ProjectADHD из recent apps без нажатия STOP. Пока FGS жив, мониторинг должен продолжаться (`stopWithTask=false`); OEM вправе остановить процесс. Challenge сохраняется в Room.
- Force-stop через Settings или перезагрузите эмулятор при active block. Окно исчезнет вместе с процессом. После открытия ProjectADHD и ручного запуска мониторинга возвращение в blocked app восстанавливает BLOCK. Автозапуск после reboot не реализован.
- Повторите process restart после успешного release: старый длинный UsageEvents интервал не должен немедленно блокировать приложение.
- Установите Stage 2 поверх Stage 1. Привычки, completed dates, выбранные приложения, лимиты и история должны остаться; старые события отображаются «Уведомление Stage 1». В Room версия 2.
- Запустите `Stage2DatabaseTest`: он создаёт реальную схему 1 из asset, мигрирует через AppDatabase и проверяет сохранённые записи; второй тест проверяет active block/release при закрытии и повторном открытии БД.

## Debug без ожидания лимита

Включите monitoring и выберите тестовое приложение с ещё не достигнутым лимитом. Откройте Главная → шестерёнка → Для разработчика → Отладка. В Debug нажмите «Тест блокирующего окна» и в течение 30 секунд откройте выбранное приложение. Окно появится на ближайшем poll, без создания BlockSession/события/cooldown; через 10 секунд исчезнет. Сам ProjectADHD не перекрывается даже тестом. Повторите с «Тест похвалы» — 4 секунды. Настоящий BLOCK имеет приоритет, поэтому перед preview очистите/закройте старые challenges.

Кнопки Refresh, Test notification, pure simulation, Clear active blocks и Clear history проверьте отдельно. Release APK не содержит Debug destination; `BuildConfig.DEBUG` также защищает вооружение теста.

## Визуальная и платформенная проверка

1. На launcher должен быть счастливый маскот из reference 08 на зелёно-голубом фоне. Проверьте круглую и squircle маску, themed icons, API 24–25 fallback. Если launcher кеширует старый значок, перезапустите launcher; при проверке миграции не удаляйте данные приложения.
2. На Home, Habits, Apps, Statistics, Profile и Debug должен быть `07_background_main.png` без растяжения. Settings — однотонный тёмный фон. На основных карточках — насыщенный фиолетовый, тёмная обводка и белый текст; в Settings карточки спокойнее.
3. На Home проверьте прогресс 0/2, 1/2, 2/2, карточки «Меньше отвлечений» и «Мой день», переходы и возврат Back. Состояние мониторинга остаётся доступным при прокрутке. На Home нет кнопок выдачи разрешений; они находятся в Settings → Разрешения.
4. В Apps быстро прокрутите список, введите поиск, обновите, поверните экран. Иконки должны соответствовать своим пакетам. Удалите тестовое приложение, вернитесь: нет падения, сохранённая строка показывает fallback и недоступность; отслеживание можно отключить. После обновления/переустановки приложения и обновления списка должна появляться актуальная иконка.
5. BLOCK должен показывать «Пора заняться делом!», реальное приложение, минуты, число оставшихся дел, инструкцию и «Посмотреть дела». В PRAISE — happy-маскот с закрытыми от радости глазами; вокруг нет белого квадрата или градиента из reference.
6. Проверьте portrait/landscape, маленький экран и увеличенный системный шрифт: BLOCK прокручивается, CTA достижима; на Home карточки читаемы поверх фона, прозрачность маскота сохранена. Praise не должен надолго закрывать экран. Проверьте отсутствие утечек WindowManager при закрытии сервиса и permission revoke.

Запишите API/OEM, navigation mode, время фактического появления/скрытия окна, build/test output и скриншоты. Для API с защищёнными окнами/приложений с hideOverlayWindows запишите отдельный результат: Android может скрыть overlay без обнаруживаемой ошибки, абсолютная блокировка не обещается. Multi-window, PiP и дополнительные дисплеи — отдельные ограничения pre-alpha.
