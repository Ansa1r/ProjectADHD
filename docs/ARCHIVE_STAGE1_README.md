# ProjectADHD — Stage 1

Локальное Android-приложение для привычек и осознанного использования телефона. Пользователь выбирает приложения, задаёт лимит непрерывной сессии и явно включает мониторинг. При достижении лимита приложение отправляет уведомление и сохраняет событие.

**Состояние проверки:** исходники Stage 1 подготовлены. Сборка Android и JUnit в среде подготовки не выполнены: Gradle Wrapper остановился на загрузке дистрибутива с `java.net.SocketException: Network is unreachable`; Android SDK и эмулятора нет. Успешная компиляция и работа на телефоне пока не подтверждены. Подробности: [BUILD_REPORT.md](docs/BUILD_REPORT.md).

## Что реализовано

- Привычки: создание, изменение, удаление, включение, выполнение сегодня и отмена выполнения. Одна отметка на привычку и местную календарную дату; удаление привычки удаляет её отметки.
- Список запускаемых приложений через PackageManager, поиск, исключение самого ProjectADHD. Выбор и лимиты 1–180 минут, по умолчанию 15. Отключение сохраняет лимит; удалённое приложение можно убрать из списка.
- Usage Access, разрешение уведомлений и состояние обоих каналов. После возврата из настроек разрешения перечитываются.
- Непрерывные сессии через UsageEvents, чистый Kotlin SessionTracker, InterventionEngine с типизированным решением.
- Пользовательский запуск/остановка foreground service, постоянное уведомление с кнопкой остановки. Проверка примерно каждые 5 секунд без wakelock.
- Уведомление при достижении лимита, название приложения, длительность и число незавершённых активных привычек. Нажатие открывает приложение.
- Общий cooldown 30 минут, настраиваемый в диапазоне 1–180. Его отметка хранится в DataStore и не удаляется при очистке истории.
- Главная, Привычки, Приложения, Статистика, Настройки и Отладка только в debug-сборке. Русский интерфейс, Material 3, системная светлая/тёмная тема.
- Использование сегодня по событиям Android, история последних 200 вмешательств на экране; в Room история не обрезается.
- 46 JUnit-тестов: движок, сессии, дневная статистика, календарные границы. Три instrumentation-теста: package, сохранение Room и запуск/навигация Compose.

Нет маскота, overlay, AccessibilityService, AI, аккаунтов, сервера, рекламы и телеметрии. Разрешение INTERNET отсутствует. Автоматическое облачное резервное копирование и перенос данных исключены настройками backup. Данные хранятся в приватном каталоге приложения; удаление приложения удаляет данные.

## Стек и требования к сборке

Один модуль `:app`, Kotlin, Compose, Navigation Compose, Material 3, ViewModel/StateFlow, Room/KSP2, DataStore Preferences, coroutines. Ручной `AppContainer` в `ProjectADHDApplication`, без Hilt/Koin.

| Параметр | Значение |
| --- | --- |
| Namespace / applicationId | `com.ansa1r.projectadhd` |
| minSdk | 24 (Android 7.0) |
| compileSdk / targetSdk | 37 |
| AGP / Gradle Wrapper | 9.4.1 / 9.6.0 |
| Kotlin / Compose compiler plugin | 2.2.10; Kotlin встроен в AGP |
| Compose BOM | 2026.02.01 |
| Room / KSP | 2.8.5 / 2.3.6 |
| DataStore / Navigation | 1.1.7 / 2.9.5 |
| JVM Gradle daemon | 25, сохранено из исходного проекта |
| Java bytecode target | 11, сохранено из исходного проекта |

Версии находятся в `gradle/libs.versions.toml`. Исходные версии AGP, Kotlin, Compose, SDK, Wrapper и критерий JVM не понижались. Нужны Android Studio с поддержкой AGP 9.4, установленный Android SDK Platform 37 и SDK Build Tools 36.0.0. Для первой синхронизации нужен доступ к Google Maven, Maven Central, Gradle Plugin Portal и серверу дистрибутива Gradle. Сеть нужна инструментам сборки на компьютере; само приложение сетевых запросов не выполняет.

`gradle/gradle-daemon-jvm.properties` выбирает JDK 25. Gradle использует локальный подходящий JDK либо настроенное автоматическое получение toolchain. Для полностью локальной сборки заранее установите JDK 25 и SDK 37. Не добавляйте локальные пути JDK/SDK в Git.

## Установка проекта из ZIP

1. Сделайте резервную копию локального проекта.
2. Распакуйте **содержимое** `ProjectADHD_Stage1.zip` прямо в корень репозитория, подтвердив замену файлов. В архиве нет дополнительной внешней папки.
3. Откройте корневую папку в Android Studio и выполните Gradle Sync.
4. При необходимости установите компоненты SDK, указанные выше. Android Studio создаст локальный `local.properties` сама.
5. Выберите `app`, вариант `debug` и запустите на телефоне Android 7.0+ либо эмуляторе. Для проверки мониторинга предпочтителен физический телефон.

Kotlin-код перенесён в `app/src/main/kotlin/com/ansa1r/projectadhd`, тесты — в аналогичные `src/test/kotlin` и `src/androidTest/kotlin`. В Gradle заданы именно эти корни исходников. Это важно: обычная распаковка ZIP не удаляет старые шаблонные файлы в `src/*/java`. Они останутся вне компиляции и не требуют ручного удаления. Новый архив старых исходников не содержит. Gradle Wrapper сохранён полностью, включая JAR.

Смена applicationId создаёт отдельное приложение Android. Данные старого шаблонного приложения не переносятся. Удалённый GitHub-репозиторий при подготовке этого архива не изменялся.

PowerShell, из корня проекта:

```powershell

.\gradlew.bat assembleDebug
.\gradlew.bat connectedDebugAndroidTest
```

В обычном cmd команды те же, без начального `.\`:

```bat
gradlew.bat testDebugUnitTest
gradlew.bat assembleDebug
```

Linux/macOS:

```bash
chmod +x gradlew
./gradlew testDebugUnitTest
./gradlew assembleDebug
./gradlew connectedDebugAndroidTest
```

Последняя команда требует подключённого устройства/эмулятора. APK появится в `app/build/outputs/apk/debug/` только после успешной сборки. APK и кеши в поставляемый ZIP не включены.

Дополнительно, при наличии Python 3.11+: `python tools/verify_source.py`. Это проверка структуры, XML, ресурсов, SQL и контрактов исходников, **не замена Kotlin-компиляции, JUnit или Android lint**.

## Первый запуск и разрешения

1. Добавьте привычку на вкладке «Привычки».
2. На вкладке «Приложения» отметьте приложение. Для короткого теста поставьте лимит **1 минута**.
3. На главной нажмите «Выдать доступ к статистике», выберите ProjectADHD в системных настройках и включите доступ. Это специальное разрешение `PACKAGE_USAGE_STATS`, не обычный runtime-диалог.
4. Разрешите уведомления. На Android 13+ появится запрос `POST_NOTIFICATIONS`. При постоянном отказе воспользуйтесь кнопкой «Настройки уведомлений». На более старых Android проверьте общий переключатель уведомлений.
5. Убедитесь, что включены оба канала: «Состояние мониторинга» и «Напоминания о лимитах».
6. Нажмите «Начать мониторинг». Должно появиться постоянное системное уведомление.
7. Откройте выбранное приложение и оставайтесь в нём до достижения лимита. При свободном cooldown появится напоминание.
8. Вернитесь в «Статистику»: событие будет в истории. При возврате сам ProjectADHD становится текущим приложением, поэтому на главной уже может отображаться он.
9. Остановите мониторинг на главной либо кнопкой в постоянном уведомлении.

`FOREGROUND_SERVICE` и `FOREGROUND_SERVICE_SPECIAL_USE` объявлены в manifest и не запрашиваются runtime-диалогом. `QUERY_ALL_PACKAGES`, `SYSTEM_ALERT_WINDOW`, разрешения Accessibility, root и wakelock не используются. Список приложений ограничен launchable Activity текущего профиля через `<queries>`.

Хотя Android технически допускает FGS без POST_NOTIFICATIONS, Stage 1 требует уведомления и включённые каналы для прозрачного мониторинга и работающего вмешательства. Без разрешений экран привычек и настройки остаются доступными. При отзыве разрешений во время работы сервис останавливается при очередной проверке; Android может самостоятельно завершить процесс ещё раньше.

## Архитектура

```text
app/src/main/kotlin/com/ansa1r/projectadhd/
  MainActivity.kt                 Compose и навигация
  ProjectADHDApplication.kt       AppContainer
  AppContainer.kt                 Ручная сборка зависимостей
  navigation/                     NavHost и основные маршруты
  ui/                             Экраны, ViewModel, UiState, компоненты, тема
  domain/                         SessionTracker, дневные интервалы, модели
    intervention/                 InterventionEngine и sealed-решения
  data/
    local/dao/                    SQL-запросы Room
    local/entity/                 Четыре сущности
    repository/                   Операции с данными и Flow
    preferences/                  DataStore: cooldown и служебные отметки
  monitoring/                     Разрешения, PackageManager, UsageEvents, FGS
  notification/                   Каналы и уведомления
  util/                           Дата, время, форматирование
```

UI получает StateFlow от ViewModel; ViewModel обращается к репозиториям и платформенным компонентам. Composable не читает Room или UsageStatsManager. Движок и логика интервалов не зависят от Android. Мониторинг не зависит от жизненного цикла Activity. Реальное состояние сервиса хранится только в процессе; сохранённая настройка никогда не выдаётся за доказательство того, что сервис работает.

Room версии 1 хранит привычки, отметки, приложения и вмешательства. Composite primary key `(habitId, localDate)` исключает дубликаты. Foreign key с CASCADE очищает отметки удалённой привычки. KSP экспортирует схему в `app/schemas` при сборке; для будущих изменений нужны явные миграции, destructive fallback не включён. История хранит название приложения и лимит на момент события.

## Семантика сессий и cooldown

- Начало сессии берётся из timestamp события Android. Переход в другое приложение завершает предыдущую сессию; возвращение начинает новую.
- Короткий переход между Activity одного пакета до 1 секунды сохраняет начало сессии. Во время PAUSED активная сессия не выдаётся движку. STOPPED не завершает активную сессию: для этого используется PAUSED. Публичный UsageEvents предоставляет className, но не идентификатор экземпляра Activity; поэтому STOPPED после нового RESUMED может относиться к старому экземпляру. Одновременные экземпляры одного класса и потерянные PAUSED дают неоднозначность.
- Блокировка, погашенный экран и события завершения устройства сбрасывают сессию. Работа только с аудио в фоне не считается непрерывной foreground-сессией.
- Лимит достигается при `duration >= limit`. Наличие привычек не является условием: если их нет, уведомление показывает 0.
- Cooldown общий для всех приложений. Сессия продолжается после уведомления; следующее возможно после окончания cooldown. Переходы между приложениями не обходят cooldown.
- Перед отправкой уведомления сохраняется резервация cooldown. После принятия уведомления NotificationManager записывается история. Android-уведомление, DataStore и Room не образуют общей транзакции: при сбое между этими действиями может остаться cooldown без события или уведомление без строки истории. Приоритет — исключить спам; ошибка останавливает сервис.
- Принятие уведомления системой не гарантирует, что пользователь его увидел: действуют настройки канала, режим «Не беспокоить» и настройки экрана блокировки.
- День привычек определяется местной датой; смена даты/часового пояса перечитывается примерно раз в секунду при активной подписке. Во время мониторинга число привычек вычисляется заново на каждом цикле.

## Отладка

Кнопка «Отладка» находится в верхней панели **только debug-сборки**. В release маршрут и кнопка отсутствуют.

Экран показывает package, build type, разрешения и каналы, реальное состояние сервиса, foreground package/name, начало/длительность сессии, решение движка, cooldown, последнее вмешательство, отметку резервации cooldown, запуск сервиса и количество записей четырёх таблиц Room.

- «Обновить» перечитывает разрешения; состояние сервиса приходит через StateFlow с его обычным интервалом.
- «Тестовое уведомление» отправляет явно помеченный тест без записи истории или изменения cooldown.
- «Симулировать вмешательство» передаёт движку 20 минут сессии, лимит 15 минут и две незавершённые привычки. Показывает решение, не меняет UsageStats и ничего не отправляет.
- «Очистить историю вмешательств» требует подтверждения, удаляет только историю и сохраняет cooldown.

Для повторного теста реального уведомления можно поставить cooldown 1 минуту и дождаться его истечения. Подробный сценарий: [MANUAL_TESTS.md](docs/MANUAL_TESTS.md).

## Ограничения Stage 1

1. Это опрос UsageEvents, а не гарантированный системный callback. Интервал около 5 секунд даёт соответствующую задержку; OEM, нагрузка, энергосбережение и Doze могут её увеличить. Нет обещания безотказного мониторинга 24/7.
2. `specialUse` выбран для пользовательского локального мониторинга, не подходящего к медиа, геолокации или dataSync. В manifest есть описание subtype. Этот выбор не гарантирует одобрение Google Play: при публикации потребуется обоснование типа в Play Console и проверка Google. Stage 1 рассчитан на локальное тестирование.
3. Запуск выполняется только из видимого приложения. Нет BOOT_COMPLETED, WorkManager-подмены непрерывного мониторинга, скрытого автозапуска или START_STICKY. После перезагрузки, force stop, остановки в системном диспетчере или гибели процесса нужно открыть приложение и нажать кнопку снова. Удаление задачи из списка последних само по себе не останавливает FGS, но прошивка может его завершить.
4. Экран выключен/заблокирован: приложение не держит устройство бодрствующим. При разблокировке требуется новое достоверное событие foreground; до него статус может быть «не определено».
5. Пустой ответ UsageEvents не позволяет отличить отсутствие новых переходов от пропущенных системой событий. Пока приложение остаётся открытым, сессия продолжает отсчитываться по последнему событию; если OEM потерял PAUSED, оценка может быть завышена. Никаких скрытых API для устранения этого ограничения нет.
6. Дневная статистика интегрируется по UsageEvents от местной полуночи. Для восстановления сессии через полночь берутся также события предыдущих 24 часов. При удалённых/недоступных событиях или необычно длинной сессии данных может не хватить. Это диагностическая оценка, не точная копия системного Digital Wellbeing.
7. Multi-window/PiP учитываются по последнему RESUMED-пакету. Одновременная видимость нескольких приложений не означает, что внимание пользователя принадлежит конкретному из них. Рабочие и чужие профили не отслеживаются.
8. При скачке системного времени сессия сбрасывается, чтобы не получить ложную большую длительность. Сохранённый timestamp cooldown из будущего блокирует повторное уведомление до выравнивания часов.
9. Маскот, overlay и AccessibilityService отсутствуют. На этом этапе вмешательство — обычное уведомление.
